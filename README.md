# 招标采购核对助手

本工具包含两个核对页面：

1. **招标延期核对**：输入招标公告列表页地址，沿同站点“下一页”抓取详情页，按项目编号归并公告并核对当前投标截止时间；
2. **开标批次核对**：输入记录目录 URL 和批次号，读取各标段企业唱标明细与人数/最低报价汇总，核对汇总是否漏记投标人，供决定是否补录。

## 一、招标延期核对

采购代理人核对招标延期时，需要找回原公告与后续更正公告。本工具输入招标公告**列表页地址**，
沿同站点“下一页”自动抓取详情页，按字段标签读取项目编号、公告类型、发布时间、投标截止时间，
按**项目编号归并**、按**发布时间先后**处理，并在浏览器展示每个项目的当前结果与全部公告链接。

### 处理规则

| 情形 | 处理结果 |
| --- | --- |
| 更正/延期公告**明确写出新的投标截止时间** | 用新时间**替换**旧时间，状态为“有效” |
| 较晚公告**声明延期却未给出新时间** | 状态标为 **“待核实”**，不再显示/沿用旧截止时间 |
| 所有公告均未公布截止时间 | 状态为“未公布” |
| 只有原始招标公告 | 沿用原截止时间，状态为“有效” |

同一项目的全部公告（原公告、更正、延期）按发布时间升序保留，并附原文链接，便于回溯核对。

## 二、开标批次核对

采购代理人开标后，需要核对唱标汇总是否漏记投标人，以决定是否补录。页面地址为 `/bid-check`，
输入**记录目录首页 URL**和**批次号**，程序沿同站点分页读取目录中的各标段：

- **企业唱标明细**：统一社会信用代码、企业名称、唱标报价；
- **人数/最低报价汇总**：投标人数、最低唱标报价。

### 处理规则

| 情形 | 处理结果 |
| --- | --- |
| 目录、明细、汇总的批次修订号一致，抓取完整，人数与最低报价均匹配 | **一致** |
| 修订号一致且抓取完整，但汇总人数或最低报价与明细去重结果不同 | **存在差异**，逐标段展示差异值 |
| 同一标段、同一统一社会信用代码出现不同报价 | **存在冲突**，保留全部报价及来源，冲突标段**不核算最低报价**，不任选其一 |
| 修订号不一致、页面读取失败、重读目录发现修订变化、触及抓取上限、目录/明细/汇总缺失 | **无法核定**，列出问题链接，不给出一致结论 |

补充口径：

1. 按“标段号 + 统一社会信用代码”去重；同一企业同一报价重复记录只计 1 家，不同报价标记冲突；
2. 只有修订号一致且抓取完整时才比较人数与最低报价；无法核定时只展示已读取数据与来源，不做差异比较；
3. 结束前会重新读取目录首页，若批次修订号或目录中的标段/明细/汇总链接发生变化，判定为无法核定；
4. 明细页若含同站“下一页”，会继续读取并合并各页唱标记录；汇总页若出现分页，则判为无法核定，
   避免用不完整的半页汇总作结论；
5. 仅跟随与入口同站点（协议+主机+端口一致）的目录分页、明细和汇总链接；
6. 页面逐标段展示：汇总人数、明细去重家数、人数差异、汇总最低报价、明细最低报价、报价差异、
   核对状态，以及目录页/明细页/汇总页的来源链接。

## 目录结构

```
.
├── docker-compose.yml          # 一键启动网页 + 同结构本地示例站点
├── webapp/                     # FastAPI 服务端渲染应用（Jinja2 模板）
│   ├── Dockerfile
│   ├── requirements.txt
│   └── app/
│       ├── main.py             # 路由：延期核对、开标批次核对、页面代理
│       ├── crawler.py          # 列表页/下一页/详情页抓取（仅同站点）
│       ├── parser.py           # 按字段标签解析公告详情
│       ├── merger.py           # 按项目编号归并、处理截止时间
│       ├── bidcheck.py         # 开标批次：目录/明细/汇总、修订一致性、去重与冲突
│       ├── models.py
│       ├── utils.py
│       └── templates/
│           ├── index.html      # 招标延期核对页
│           └── bid_check.html  # 开标批次核对页
├── example-site/               # 同结构本地示例站点（静态 HTML + nginx）
│   ├── Dockerfile              # 构建时运行 generate_site.py 生成页面
│   ├── nginx.conf
│   ├── generate_site.py        # 公告场景 + 6 个开标批次记录场景
│   └── site/                   # 生成产物（可重新生成）
└── tests/
    ├── test_end_to_end.py      # 延期核对端到端测试
    └── test_bid_check.py       # 开标批次核对端到端测试
```

## 用 Docker Compose 启动

```bash
docker compose up --build
```

- 网页应用：<http://localhost:8000>
- 示例站点（宿主机直连）：<http://localhost:8080>

在网页输入框中填入示例站点的列表页地址（容器内服务名地址，网页后端可直接抓取）：

```
http://example-site/list/page_1.html
```

点击“开始核对”后，页面展示：

1. 抓取概况：遍历的列表页（即“下一页”路径）、公告数、跳过链接、错误信息；
2. 各项目当前核对结果：项目编号、名称、状态徽章、**当前**投标截止时间；
3. 每个项目可展开的公告历史：公告类型、是否声明延期、发布时间、原文截止时间及链接。

开标批次核对页（<http://localhost:8000/bid-check>）输入记录目录首页与批次号，例如：

```
目录 URL：http://example-site/records/B2026-001/index.html
批次号： B2026-001
```

也可以把批次选择页 `http://example-site/records/index.html` 作为目录 URL，程序会按批次号定位到对应批次目录。

页面会展示整体核定状态、问题链接、批次修订号来源，以及逐标段的人数/最低报价差异和来源链接；
若存在同一企业不同报价，还会单列报价冲突及全部报价来源。

> 公告链接默认指向容器内网地址（如 `http://example-site/...`），宿主机浏览器无法直接打开，
> 因此页面链接统一经过网页后端的 `/view` 代理打开；示例站点本身也映射在 8080 端口可直接浏览。

## 解析器的字段适配

详情页解析不绑定固定模板，按“字段标签 → 值”依次尝试：

1. 表格行（`th/td`，含一行两对字段）；
2. `dl/dt/dd` 定义列表；
3. `label` + 输入控件（`input/textarea/select`）；
4. 正文中的“标签：值”段落。

标签支持常见别名（如“招标项目编号/项目编码”“投标文件递交截止时间/开标时间”等），
标签缺失时再用正则兜底；识别不到项目编号的页面会被跳过并记入“跳过链接”。

## 安全与边界

- 仅跟随与入口**同站点**（协议+主机+端口一致）的“下一页”、明细和汇总链接，跨站链接跳过并记录；
- 只允许 `http(s)`，拒绝 `file://` 等协议；
- 延期核对上限：列表页 10 个、详情页 100 个、单请求超时 15 秒；
- 开标批次核对上限：目录页 10 个、明细页 100 个、汇总页 100 个、标段 200 个、单请求超时 15 秒；
  触及任一上限即判为无法核定，并给出未读取页面的链接；
- `/view`、`/asset` 代理同样只转发 `http(s)` 目标。
